# Proposal: PSP Webhook Authentication

## Intent

Close issue #13. The PSP callbacks `/api/psp/webhook/cashin` and `/api/psp/webhook/payout` move money without authenticating the caller. A forged cash-in callback can credit a user balance; a forged payout `FAILED` callback can refund a withdrawal that the PSP actually paid.

## Evidence

- Both handlers act on the JSON body alone; no header, signature, token, or IP check exists.
- The PSP client only authenticates outbound calls (`X-API-Key`); the PSP offers no documented callback signature in the codebase.
- Callback URLs are registered per request (`clientCallbackUrl`, `callbackUrl`) before the PSP assigns an id.
- The cash-in handler reads the record, then opens a transaction without a row lock; payout `COMPLETED` is not idempotent.
- Production currently has no `PSP_API_KEY`, so the PSP is not operational; the fix must land before it is enabled.

## Scope

In scope:
- Signed callback URLs generated by QuartzPlay with a new secret `PSP_WEBHOOK_SECRET`, verified in constant time before any database access.
- Fail closed: without the secret, callbacks answer 503 and new cash-in or payout requests are refused.
- Row locks and idempotency for both callbacks.
- Tests for missing, invalid, and valid authentication, and for replay.

Out of scope:
- Telegram webhook secret token (separate follow-up).
- Changing the PSP provider, amounts policy, or bonus logic.
- Setting the secret in Railway (operational step after merge, with owner approval).

## Approach

HMAC-SHA256 over a canonical, purpose-scoped message embedded as query parameters in the callback URL:
- Cash-in: `uid` (user id) and `n` (random nonce); the matched record must belong to `uid`.
- Payout: `rid` (withdrawal id); the matched record must be `rid`.

## Risks

- Callbacks for requests created before deploy carry no signature and will be rejected. Production has no PSP key, so no such requests exist; staging records, if any, are reconciled manually.
- The signature travels in the URL and may appear in PSP-side logs; it is scoped to one user or one withdrawal, never the secret itself.

## Rollback

Revert the PR. No schema change.
